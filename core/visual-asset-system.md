# Visual Asset System

Use this file to prevent decks from looking simple, generic, cheap, or "AI-generated".

The core rule: icons, images, illustrations, and decorative visuals are not filler. They must support the story, match the visual recipe, and follow a consistent asset system.

## When To Use

Use this workflow when:

- the deck feels too simple or monotonous;
- the user asks for "designer-level" or "less AI-looking" output;
- an HTML deck or visually expressive talk is requested;
- the deck uses icons, images, illustrations, screenshots, or hero visuals;
- a sample slide gate reveals weak visual quality.

## Asset Roles

Classify every visual asset by role:

| Role | Purpose | Examples |
|---|---|---|
| evidence | proves or documents a point | screenshots, charts, photos from source material |
| orientation | helps the audience navigate | icons, section markers, page labels |
| metaphor | makes an abstract idea memorable | carefully chosen illustration or photo |
| texture | adds atmosphere without distracting | subtle backgrounds, gradients, patterns |
| brand | signals identity or ownership | logo, brand color, approved graphic system |

Do not use visuals only because a slide feels empty.

## Icon Rules

Avoid:

- random emoji as business icons;
- mixed icon styles;
- over-detailed icon sets;
- decorative icons that do not encode meaning;
- icons pulled from unclear-license sources.

Prefer:

- one icon family per deck;
- simple line or solid style, not both;
- consistent stroke width;
- consistent corner radius;
- icons only for repeated categories or navigation;
- source or license notes for external icon sets.

## Image Rules

Avoid:

- generic stock photos;
- image styles that fight the template recipe;
- low-resolution or watermarked images;
- private screenshots without permission;
- images that introduce emotional tone inconsistent with the audience.

Prefer:

- image concepts defined before search or generation;
- consistent crop ratio;
- consistent color treatment;
- clear rights and attribution where required;
- screenshots only when they are evidence or demo content.

## Illustration Rules

Use illustrations only when they make the idea clearer or more memorable.

Check:

- style consistency;
- cultural fit;
- audience fit;
- licensing;
- whether a diagram would be clearer than an illustration.

## Asset Brief

Before sourcing or generating visuals, write a short asset brief:

```text
Slide:
Asset role:
Message supported:
Desired style:
Forbidden style:
Source or generation route:
Rights status:
Fallback:
```

## Visual Enrichment Pass

After the page map is approved, run a visual enrichment pass:

1. Identify slides that are too text-only or monotonous.
2. Decide whether the slide needs a diagram, chart, image, icon, or stronger layout instead of decoration.
3. Create asset briefs for required visuals.
4. Confirm rights or use placeholders.
5. Build 1-2 sample slides before applying the asset system deck-wide.

## QA Checks

Before delivery:

- asset style is consistent;
- assets support the message;
- no random emoji or mixed icon styles;
- image rights are clear or placeholders are used;
- screenshot privacy is cleared;
- visuals do not reduce readability;
- the deck still matches the selected recipe and audience.

## Public Repository Rule

Do not commit third-party images, icons, screenshots, downloaded asset packs, or generated private visual assets into the public repository.

Public repository content may include:

- asset-selection rules;
- fictional examples;
- placeholder asset briefs;
- original redistributable seed assets if rights are clear.
